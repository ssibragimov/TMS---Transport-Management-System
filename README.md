# Платформа учёта спецтранспорта и ГСМ аэропортов Узбекистана

Мультиофисная система для служб спецтранспорта: единый учёт техники, водителей,
топлива и путевых листов по всем аэропортам страны с изоляцией данных на уровне СУБД.

## Демонстрационные данные

`npm run db:seed` создаёт только справочники: права, роли, 13 офисов, виды
топлива, модели техники и нормы расхода. Операционных данных в нём нет.

Чтобы наполнить платформу правдоподобным содержимым:

```powershell
npm run db:seed:demo
```

Скрипт разворачивает три аэропорта с историей за 30 дней — Ташкент (крупный
парк), Самарканд (средний) и Бухару (минимальный). Одинаковые модели техники
в разных офисах заданы намеренно: только так работает сравнение расхода между
аэропортами.

Генерация детерминированная — повторный запуск даёт те же данные, поэтому
на конкретный путевой лист можно ссылаться в обсуждении. Скрипт **пересоздаёт**
операционные данные этих трёх офисов (путевые листы, движение ГСМ, наряд-заказы,
алерты) и отказывается работать при `NODE_ENV=production`.

|---|---|---|

Те же пять ролей заведены для Самарканда (`.skd`) и Бухары (`.bhk`) — удобно
проверять, что сотрудник одного аэропорта не видит данные другого.

**Смените пароль администратора до выхода в эксплуатацию.**

### Что заложено в данные специально

- У одного водителя в каждом офисе **допуск на перрон просрочен**, у второго
  истекает на этой неделе — иначе дашборд сроков не на чем проверить.
- Две-три единицы техники в парке «прожорливее» остальных и стабильно дают
  перерасход у разных водителей. Это проверка того, что аналитика указывает
  на технику, а не на людей.
- Часть парка стоит в ремонте и на ТО: полностью исправного парка не бывает.
- Остатки в ёмкостях за месяц выработаны неравномерно, по одной ёмкости
  остаток близок к минимуму.

## Запуск без Docker и без прав администратора

Так проект развёрнут на этой машине. Node.js и PostgreSQL лежат портативно
в `.tools/` (папка в `.gitignore`), в системе ничего не устанавливается.

Ограничение: в портативной сборке PostgreSQL нет **PostGIS** и **TimescaleDB**,
поэтому блок телеметрии отключён через `SKIP_SQL=03_telemetry.sql` в `.env`.
На остальные модули это не влияет — телематика начинается с этапа 8.

```powershell
# Node в PATH только для текущей сессии терминала
$env:Path = 'D:\GSM PROJECT\.tools\node;' + $env:Path

# PostgreSQL слушает 5433
.\.tools\pgsql\bin\pg_ctl.exe -D .\.tools\pgdata -l .\.tools\pg.log -o "-p 5433" start
.\.tools\pgsql\bin\pg_ctl.exe -D .\.tools\pgdata stop     # остановить

npm run dev
```

Миграции в такой среде применяются командой `prisma migrate deploy`:
`migrate dev` требует интерактивного терминала и в скриптах не работает.
Новая миграция создаётся так:

```powershell
cd apps\api
npx prisma migrate diff --from-migrations prisma\migrations `
  --to-schema-datamodel prisma\schema.prisma --shadow-database-url $env:DATABASE_URL `
  --script --output prisma\migrations\<метка>_<имя>\migration.sql
npx dotenv -e ..\..\.env -- prisma migrate deploy
```

## Управление пользователями

Раздел «Пользователи» в меню (виден при праве `user.read`) — две вкладки.

**Пользователи.** Создание учётной записи с назначением офисов и ролей.
Ключевое: **роль выдаётся в разрезе офиса** — один человек может быть
диспетчером в Ташкенте и наблюдателем в Самарканде. В форме это отдельные
строки, а при переключении офиса набор прав в токене меняется соответственно.
Также доступны сброс пароля администратором и блокировка учётной записи —
обе операции немедленно завершают все сессии пользователя.

**Роли и права.** Просмотр девяти системных ролей с их наборами прав и
создание собственных. Права сгруппированы по разделам (транспорт, ГСМ,
путевые листы…), у неочевидных есть пояснения. Системные роли можно
изменять, но не удалять; своя роль не удаляется, пока назначена хоть кому-то.

Два ограничения заложены намеренно:

- Назначить офис вне своей области видимости нельзя — проверка на сервере,
  а не только в форме. Администратор Бухары не выдаст доступ к Ташкенту.
- Признак обхода изоляции офисов (`bypass_rls`) через API не выставляется
  ни при каких условиях. Это свойство технической учётки, задаётся seed'ом
  или вручную в БД.

## Администрирование

Раздел «Администрирование» (право `dictionary.read`) — справочники платформы.

Справочники разделены на два класса, и это принципиально:

- **Общестрановые** — виды топлива, модели техники, номенклатура запчастей.
  Одни на все аэропорты, RLS на них не действует. Иначе сравнить расход
  одинаковых тягачей в Ташкенте и Бухаре было бы нечем: в каждом офисе
  завелась бы своя «COBUS 3000», и отчёты перестали бы сходиться.
- **Офисные** — подразделения и контрагенты. Свои у каждого аэропорта,
  изолируются как обычные прикладные данные.

Отдельная вкладка «Офисы и аэропорты» — подключение нового аэропорта.
Код офиса участвует в номерах документов (`PL-TAS-2026-000123`) и после
создания не меняется. Зимняя надбавка к норме расхода задаётся здесь и
применяется ко всей технике офиса — у каждого региона она своя.

Удаление везде щадящее: если на запись есть ссылки, она не удаляется,
а отключается. Справочник, из которого можно выдернуть строку, ломает
документы за прошлые периоды.

## Журнал действий

Раздел «Журнал действий» (право `audit.read`) — только чтение. Записи нельзя
изменить или удалить ни через интерфейс, ни через API: журнал, который можно
подчистить, бесполезен при разборе.

Для изменений сохраняются **только реально изменившиеся поля** — снимок «до»
читается перед выполнением операции и сравнивается с телом запроса. В карточке
записи видно «было → стало» по каждому полю. Пароли и токены не попадают
в журнал ни в каком виде.

Операции над вложенными объектами не выдают себя за операции над родителем:
удаление фотографии пишется как `VehiclePhoto`, а не как `Vehicle` — иначе
запись читалась бы как списание техники.

Снимок «до» доступен не для всего. Составные операции (выдача ГСМ меняет
и документ, и остаток ёмкости) записываются без него: снимок по одной таблице
был бы обманчив.

## Файлы и фотографии

Фотографии техники загружаются в карточке, вкладка «Фотографии»: JPEG, PNG,
WebP и HEIC до 10 МБ. Одно фото помечается главным — оно показывается в списке.

Файлы **не раздаются статикой**: доступ идёт через API с проверкой прав и
принадлежности офису. Прямая раздача из папки обошла бы изоляцию — достаточно
было бы угадать ссылку.

Хранилище сейчас — локальный диск (`storage/` в корне, в git не попадает).
Это выбор первого этапа: MinIO поднимается только вместе с Docker, а
разворачивать систему приходится и там, где его нет. Интерфейс `StorageService`
намеренно узкий (save / read / remove), чтобы переход на S3 свёлся к одному классу.

## Как устроена изоляция офисов

Это главное архитектурное решение проекта — прочитайте до того, как писать новый модуль.

1. Почти каждая таблица несёт `office_id`.
2. API подключается к БД **прикладной ролью** `gsm_app`, на которую действуют
   политики RLS. Миграции и seed идут под владельцем `gsm_owner`, который их обходит.
3. Перед каждым запросом расширение Prisma выставляет `app.office_ids` —
   список офисов из JWT текущего пользователя.
4. Политика в PostgreSQL сверяет `office_id` строки с этим списком.

Практическое следствие: **забытый `WHERE office_id = ...` не приводит к утечке**.
Запрос физически не вернёт чужие строки. Но фильтр всё равно пишите — RLS
это страховка, а не замена бизнес-логике.

При старте API проверяет, что подключение идёт не под владельцем и не под
суперпользователем. Если проверка не прошла, в development пишется ошибка в лог,
в production приложение не стартует.

## Что делать дальше

Ближайшие шаги в порядке приоритета:

1. **Собрать реальные формы.** Печатная форма путевого листа должна быть
   согласована с бухгалтерией **до** её разработки — переделка потом дороже.
   Сейчас `/waybills/:id/print` отдаёт только данные, без вёрстки.
2. **Заменить нормы расхода.** В seed заложены ориентировочные значения
   с пометкой в поле `documentRef`. Реальные нормы утверждаются приказом
   по предприятию и отличаются между аэропортами. Экрана управления нормами
   пока нет — правятся через API или Prisma Studio.
3. **ТО и ремонты** — схема БД есть, нужен API и интерфейс.
4. **Топливные карты** — модель есть, операций с ними нет.
5. **Сводная отчётность по стране** (право `report.cross_office`): сейчас
   все списки и отчёты ограничены активным офисом.
6. **Телематика** — приёмник данных с трекеров и сверка GPS-пробега
   с пробегом в путевых листах.
7. **Загрузка сканов** — поля `file_key` в схеме есть, MinIO поднимается
   в docker-compose, но загрузки файлов в API пока нет.

## Замечания по эксплуатации

- **Резервное копирование** настройте до загрузки реальных данных. `pg_dump`
  раз в сутки плюс WAL-архивирование.
- **Часовые пояса.** Ферганская долина и Каракалпакстан живут в одном
  государственном времени, но у офисов заложено поле `timezone` — на случай
  расхождения смен. Все отметки времени в БД хранятся в `timestamptz`.
- **Нумерация документов** идёт без пропусков в разрезе офиса и года.
  Не заменяйте её на sequence PostgreSQL: пропущенный номер в журнале
  путевых листов придётся объяснять проверяющему.
- **Мягкое удаление.** Ничего из того, на что ссылаются документы,
  физически не удаляется. Отчёт за позапрошлый год должен собираться
  и после списания техники.
